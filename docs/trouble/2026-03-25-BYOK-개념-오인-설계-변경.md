# BYOK 개념 오인으로 인한 설계 변경 기록

- 작성일: 2026-03-25
- 상태: 확정
- 관련 범위: provider 연동, API 설계, 설정 UI, MVP 작업 체크리스트

## 1. 문제 상황

초기에는 ThinkWrite MVP의 provider 연동을 **앱 내부 BYOK UX**로 해석했다.

이 해석에 따라 다음과 같은 방향으로 설계를 진행했다.

- `POST /api/keys`, `GET /api/keys`, `DELETE /api/keys` 같은 key 관리 API 추가
- 앱 내부에 provider 선택 / API Key 입력 / 저장 / 삭제 / 등록 상태 조회 UI를 둘 계획 수립
- 서버에 key를 영구 저장하고 관리하는 구조를 MVP 기본안으로 간주

하지만 이후 요구를 다시 확인하는 과정에서, 실제 의도는 다음에 더 가까웠다.

- 이 프로젝트는 다중 사용자 SaaS 운영이 아니라 **오픈소스 self-hosted MVP**에 가깝다.
- API Key는 각 실행자가 **자기 환경의 `.env.local`** 에 넣어 관리하면 된다.
- 현재 MVP에서 검증하려는 핵심은 **Ghost Complete 흐름**이지, 앱 내부 key 등록 UX가 아니다.

즉, **BYOK를 “앱 안에서 사용자가 key를 등록하는 UX”로 오해한 것**이 설계 과잉의 원인이었다.

---

## 2. 오인한 개념과 실제 의도 차이

### 잘못 잡았던 해석

- BYOK = 사용자가 앱 설정 화면에서 provider와 API Key를 직접 입력
- 앱은 key 등록/조회/삭제 API를 제공
- 서버 또는 DB가 그 key를 저장하고 관리

### 실제 의도

- BYOK = 각 실행 환경이 자기 key를 직접 준비
- 앱은 서버 `.env.local`에 설정된 `OPENAI_API_KEY`를 읽어 사용
- 앱 내부에는 key 등록/삭제 UI를 두지 않음

---

## 3. 왜 설계 실수였는가

초기 설계는 현재 MVP 목표보다 범위가 컸다.

### 불필요하게 늘어난 범위

- key 저장/조회/삭제 API
- key 등록 상태 UI
- key 저장소/암호화/삭제 정책
- 다중 사용자 운영을 전제한 보안 경계 설계

### 실제 MVP에서 더 중요한 것

- editor 흐름
- prefix / suffix 기반 completion 요청
- OpenAI 호출 성공/실패 처리
- ghost text 렌더링과 상호작용

결과적으로 앱 내부 BYOK UX는 **나중에 제품 범위가 커졌을 때 다시 검토하면 되는 항목**인데, 초기 MVP에서 너무 앞당겨 설계한 셈이 됐다.

---

## 4. 설계 변경 내용

다음과 같이 방향을 바꿨다.

### 변경 전
- provider를 요청 body나 설정 UI에서 선택하는 흐름
- `/api/keys` 기반 key 관리 API
- 앱 내부 key 저장/삭제/등록 상태 조회 UI

### 변경 후
- provider는 서버에서 **OpenAI로 고정**
- API Key는 서버 `.env.local`에서만 관리
- 클라이언트는 key 원문을 알지 못함
- 앱 내부에는 key 입력/삭제 UI를 두지 않음
- `/api/completion` 중심으로 먼저 구현

---

## 5. 실제 반영 사항

- `app/api/keys` 관련 설계 제거
- key 관리 service / use-case 제거
- `AutocompleteRequest`에서 `provider` 필드 제거
- completion 흐름을 OpenAI 고정 호출 구조로 단순화
- 문서 전반을 `.env` 기반 provider 연동 기준으로 수정
- 정적 홈 UI의 provider 영역도 `.env.local` 안내 기준으로 수정

---

## 6. 이번 변경으로 얻은 점

- MVP 구현 범위 축소
- provider 연동 핵심에 더 빨리 집중 가능
- key 저장/삭제/조회 UX 때문에 ghost 구현이 밀리는 문제 완화
- self-hosted 오픈소스 프로젝트 성격과 더 잘 맞는 구조 확보

---

## 7. 반대급부

- 앱 내부 BYOK UX는 이번 MVP에서 검증하지 못함
- 추후 다중 사용자/배포형 제품으로 확장할 때는 key 관리 구조를 다시 설계해야 함
- provider 전환 UX도 현재는 환경변수/코드 변경 중심이므로 제품 기능으로는 노출되지 않음

---

## 8. 이후 원칙

앞으로는 provider 연동 관련 논의에서 아래를 먼저 구분한다.

1. **self-hosted runtime config 문제인지**
2. **앱 내부 사용자 설정 UX 문제인지**

이 둘을 구분하지 않으면, 실제로는 runtime 설정만 필요한데도 앱 내부 설정 기능까지 함께 설계하는 과잉이 다시 발생할 수 있다.
