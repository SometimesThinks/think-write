# Ghost 요청 성공 연결 정리

- 작성일: 2026-03-30
- 상태: 진행 중
- 관련 범위: ghost complete, request trigger, editor state

## 1. 문제 상황

이전까지는 아래 항목이 각각 따로 존재했다.

- 현재 문단 기준 `prefix` / `suffix`
- ghost eligibility 조건
- `isGhostVisible`, `ghostText` 상태
- `Tab` / `Esc` 임시 키 surface

하지만 실제 completion 요청 성공이
`ghostText`와 `isGhostVisible`로 연결되지 않아,
ghost 상태가 아직 죽은 값에 가까웠다.

---

## 2. 이번에 연결한 흐름

이번에는 가장 단순한 성공 흐름만 먼저 연결했다.

1. `isGhostEligible === true`
2. request validation 통과
3. `/api/completion` 호출
4. 성공 응답이면 `ghostText = output`
5. `isGhostVisible = true`

즉, 이제 ghost 상태가 실제 completion 응답과 연결되기 시작했다.

---

## 3. 왜 이 단계가 중요하나

이전까지는 ghost 상태를 위한 그릇만 있었고,
실제 값은 항상 비어 있었다.

이번 연결 이후에는:

- `ghostText`가 provider 응답을 담을 수 있고
- `isGhostVisible`가 실제 성공 여부에 따라 바뀌고
- `Tab` / `Esc` 임시 매핑도 나중에 실제 상태 전이로 교체하기 쉬워진다

즉, 이번 단계는
**“ghost 상태를 실제 네트워크 응답과 처음 연결한 시점”**
으로 볼 수 있다.

---

## 4. 현재 구현 방식

현재는 editor 쪽 effect에서 아래 조건으로 요청을 보낸다.

- ghost eligibility 충족
- request preview가 유효함

성공 시:

- `ghostText = output`
- `isGhostVisible = true`
- console에 success log 출력

실패 시:

- `ghostText = null`
- `isGhostVisible = false`
- console에 failure/error log 출력

아직은 임시 구현이라 에러 UI 대신 log로만 확인한다.

추가로 현재 단계에서는 아래 두 가지 방어도 함께 둔다.

- `AbortController`: effect가 정리될 때 이전 진행 중 요청을 취소
- `lastRequestedKeyRef`: 직전과 같은 request payload면 중복 요청을 건너뜀

즉, 이 단계는 단순 성공 연결만이 아니라
**stale request 취소 + 직전 중복 요청 방지**까지 포함한다.

---

## 5. 아직 남은 것

이번 연결은 첫 성공 흐름만 다룬다.

아직 남아 있는 것은:

- debounce 정책과의 관계 정리
- 추가 입력 / 커서 이동 invalidation
- `Tab` 수락 시 실제 텍스트 삽입
- `Esc` dismiss 시 상태 초기화
- 실제 ghost text 렌더링

즉, 지금은 **요청 성공 → 상태 채우기 + 기본 요청 방어**까지만 된 상태다.

---

## 6. 이후 원칙

다음 단계에서는 ghost 흐름을 아래 순서로 이어간다.

1. success 응답으로 상태 채우기
2. invalidation 규칙 연결
3. `Tab` / `Esc`를 실제 상태 전이로 연결
4. editor 내부 렌더링 연결

현재 MVP에서는 우선
**요청 성공 연결 → invalidation → 수락/무시 → 렌더링**
순서로 진행한다.
