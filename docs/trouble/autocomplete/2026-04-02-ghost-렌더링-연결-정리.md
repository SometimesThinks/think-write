# Ghost 렌더링 연결 정리

- 작성일: 2026-04-02
- 상태: 진행 중
- 관련 범위: ghost complete, editor overlay, cursor position

## 1. 문제 상황

이전까지는 아래 항목만 존재했다.

- `ghostText`
- `isGhostVisible`
- completion 성공 시 상태 채우기
- `Tab` / `Esc` 임시 key surface

하지만 실제 editor 안에는 ghost text가 보이지 않아,
상태가 바뀌는지 사용자가 눈으로 확인하기 어려웠다.

---

## 2. 이번에 한 일

이번에는 ghost text를 editor 안에 실제로 보이게 연결했다.

1. editor 입력 박스에 overlay 기준 ref 추가
2. 현재 커서 좌표를 `editor.view.coordsAtPos(...)`로 읽음
3. editor surface 기준 상대 좌표로 변환
4. `ghostText && isGhostVisible`일 때 해당 위치에 ghost text 렌더링

즉, 이제 ghost 상태가 바뀌면 화면에서도 희미한 텍스트로 바로 확인할 수 있다.

---

## 3. 왜 이렇게 구현했나

처음에는 상태만 먼저 연결했지만,
ghost complete는 결국 **editor 안에서 어떻게 보이느냐**가 핵심이다.

이번 단계에서는 가장 단순한 방식으로:

- Tiptap 본문 DOM은 그대로 두고
- editor surface 안에 absolute overlay를 하나 더 올리는 방식

을 택했다.

이 방식의 장점은:

- 기존 editor 상태 관리 구조를 크게 흔들지 않음
- 현재 ghost 흐름을 빠르게 눈으로 확인할 수 있음
- 이후 accept / dismiss / invalidation을 붙이기 쉬움

---

## 4. 현재 구현 방식

현재 ghost 렌더링 조건은 아래와 같다.

- `ghostText`가 존재함
- `isGhostVisible === true`
- editor surface ref가 존재함

표시 위치는:

- 현재 selection의 `from` 위치를 기준으로 계산
- `coordsAtPos`로 커서의 화면 좌표를 얻음
- editor 입력 박스 기준 상대 좌표로 바꿔서 overlay 위치로 사용

즉, 현재 구현은
**커서 위치 기준 absolute overlay ghost 렌더링**이다.

---

## 5. 아직 남은 것

이번 단계는 렌더링만 먼저 연결한 것이다.

아직 남은 것은:

- 추가 입력 시 ghost invalidation
- 커서 이동 시 ghost invalidation
- `Esc` dismiss 실제 상태 전이
- `Tab` accept 시 editor 본문 삽입
- 줄바꿈 / 긴 ghost text / 스크롤 상황에서의 미세 조정

즉, 지금은
**상태 존재 → 화면 표시**까지 된 상태다.

---

## 6. 이후 원칙

다음 단계에서는 ghost가 보이는 것만으로 끝내지 않고,
보이는 ghost가 언제 사라지고 언제 본문에 합쳐질지까지 연결한다.

순서는 아래로 가져간다.

1. ghost 렌더링
2. invalidation
3. dismiss
4. accept

이번 단계는 그중
**ghost가 실제로 보이기 시작한 첫 렌더링 연결 단계**로 본다.
