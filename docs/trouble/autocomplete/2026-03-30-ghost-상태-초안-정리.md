# Ghost 상태 초안 정리

- 작성일: 2026-03-30
- 상태: 진행 중
- 관련 범위: ghost complete, editor state, debug surface

## 1. 문제 상황

Ghost Complete 요청 조건과 이벤트 감지 기준은 조금씩 정리되고 있었지만,
실제 ghost 자체를 표현하는 상태값은 아직 없었다.

이 상태에서는:

- 현재 ghost가 화면에 보여야 하는지 여부를 별도 상태로 다루기 어렵고
- provider 응답이 왔을 때 어떤 값을 ghost로 저장할지 기준이 없고
- 이후 `Tab` 수락 / `Esc` dismiss / invalidation을 상태 전이로 연결하기 어렵다

---

## 2. 이번에 추가한 상태

이번에는 가장 기초적인 두 상태를 먼저 추가했다.

- `isGhostVisible: boolean`
- `ghostText: string | null`

현재 단계에서는 둘 다 초기값만 들어간다.

- `isGhostVisible = false`
- `ghostText = null`

즉, 아직 ghost를 실제로 띄우는 단계는 아니고,
**ghost를 상태로 다룰 최소 그릇을 먼저 만든 단계**다.

---

## 3. 왜 이 두 값이 먼저 필요한가

### `isGhostVisible`

이 값은 ghost가 현재 보이는 상태인지 아닌지를 나타낸다.

이후 아래 조건들과 직접 연결된다.

- `Tab`을 눌렀을 때 수락 가능한지
- `Esc`를 눌렀을 때 dismiss 해야 하는지
- 추가 입력이나 커서 이동 시 invalidation 해야 하는지

즉, 상호작용의 기준점이 된다.

### `ghostText`

이 값은 provider 응답에서 받아온 ghost 후보 문자열을 담는다.

이후 아래 흐름의 중심이 된다.

- 요청 성공 → `ghostText` 저장
- ghost 표시 → `isGhostVisible = true`
- 수락 → 실제 텍스트로 반영 후 초기화
- dismiss / invalidation → `ghostText = null`

즉, 고스트 자동완성의 실제 내용을 저장하는 핵심 상태다.

---

## 4. 현재 단계의 의미

이번 구현으로 ghost 기능이 완성된 것은 아니다.

지금 된 것은:

- ghost visibility를 별도 상태로 둘 준비
- ghost text 값을 별도 상태로 둘 준비
- debug panel에서 이 두 값을 확인할 수 있는 표면 마련

아직 안 된 것은:

- provider 응답을 `ghostText`에 넣기
- `isGhostVisible`를 실제 조건에 따라 바꾸기
- ghost text를 editor 안에 렌더링하기

---

## 5. 왜 문서로 남길 가치가 있는가

이건 작은 상태 추가처럼 보이지만, 사실 ghost complete 구현의 중심 전환점 중 하나다.

이전까지는:

- request preview
- eligibility 조건
- context 추출

같은 준비 작업 위주였다면,
이제부터는 **실제 ghost를 상태로 다루는 단계**로 넘어간다.

즉, 이 두 상태는 이후 ghost state machine의 출발점이다.

---

## 6. 다음 연결 포인트

다음에는 이 두 상태를 아래와 연결해야 한다.

1. provider 성공 응답 → `ghostText` 저장
2. eligibility + 요청 성공 → `isGhostVisible = true`
3. `Tab` → accept
4. `Esc` → dismiss
5. 추가 입력 / 커서 이동 → invalidation

현재 MVP에서는 우선
**상태 추가 → 이벤트 연결 → 렌더링** 순서로 진행한다.
