- `src/server/lib/route-result.ts`에 공통 에러 응답 포맷, `requestId`, 성공/실패 응답 헬퍼를 모아 route와 하위 계층이 같은 형태를 쓰게 했다.
- completion use-case / service / adapter 골격을 `requestId`와 검증된 request를 넘기는 흐름으로 연결했다.
- `src/shared/autocomplete.ts`에서 더 이상 쓰지 않는 provider 필드를 제거해 `.env` 기반 단일 provider 방향과 타입 계약을 맞췄다.
- 서버 디렉터리의 `.gitkeep` 파일을 지우고 실제 구현 파일 구조로 전환했다.

## Why it matters
- 이 커밋은 자동완성 기능을 “호출 가능한 API” 수준으로 한 단계 올린다. 아직 OpenAI 호출은 없지만, 적어도 잘못된 요청을 early-fail 시키고 같은 에러 형식으로 응답할 수 있게 됐다.
- 특히 `requestId`를 route 진입 시 생성하도록 한 것은 이후 debounce, stale response, 에러 추적 문제를 다룰 때 기반이 된다.
- 공통 검증/응답 포맷을 먼저 만들어두면 provider 구현이 붙을 때 route가 비대해지는 것을 막고, success/error shape가 흔들리는 문제를 줄일 수 있다.
- provider 필드 제거는 self-hosted `.env` 기반 단일 provider 전략을 코드 타입에 반영한 결정이라, 문서와 구현 정합성을 높인다.

## Key files
- `app/api/completion/route.ts`: completion 요청의 HTTP 진입점으로, JSON 파싱/검증/에러 응답 흐름이 어떻게 시작되는지 보여준다.
- `src/server/lib/validate-autocomplete.ts`: prefix/suffix 기반 최소 요청 계약을 코드로 고정하는 검증 로직이다.
- `src/server/lib/route-result.ts`: requestId와 공통 에러 포맷을 한곳에 모아 이후 API 응답 일관성의 기준점이 된다.
- `src/server/use-cases/completion.ts`: 자동완성 기능 하나를 대표하는 use-case 진입점이 어떤 형태인지 보여준다.
- `src/shared/autocomplete.ts`: 클라이언트와 서버가 공유하는 request/response 타입이 제품 결정과 어떻게 연결되는지 볼 수 있다.
