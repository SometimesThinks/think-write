# ThinkWrite 기술-스택

## 1. 목적

이 문서는 ThinkWrite MVP 구현을 위한 기술 선택 현황을 정리한다.

기술 스택은 확정 항목과 미확정 항목을 구분해 관리한다.

## 2. 확정 항목

### 2.1 프레임워크

- 선택 방향: Next.js
- 결정 상태: 확정
- 선택 이유:
  - 프론트엔드와 서버 계층을 하나의 애플리케이션 안에서 함께 구성 가능
  - BYOK 구조와 API route 기반 구현에 적합
  - 오픈소스 온보딩과 초기 개발 속도 측면에서 유리
- 선택하지 않은 후보:
  - 별도 백엔드 분리 구조
- 선택하지 않은 이유:
  - MVP 단계에서 구조 복잡도가 과도하게 증가함
  - 현재 범위에서는 단일 애플리케이션으로도 충분히 구현 가능함
- 얻는 점:
  - 프론트엔드와 서버 계층을 빠르게 함께 개발 가능
  - 초기 배포 및 온보딩 단순화
  - BYOK와 API route 기반 구현에 유리
- 잃는 점:
  - 서버가 커질 경우 별도 서비스보다 구조적 한계가 빨리 드러날 수 있음
  - 장기적으로는 분리 구조보다 역할 경계가 흐려질 가능성 있음

### 2.2 에디터

- 선택 방향: Tiptap
- 결정 상태: 확정
- 선택 이유:
  - Headless 구조로 심플한 글쓰기 UI 구성에 적합
  - ProseMirror 기반으로 고스트 텍스트 렌더링과 단축키 커스터마이징에 유리
  - 관련 문서와 사례가 비교적 풍부함
- 선택하지 않은 후보:
  - Lexical
- 선택하지 않은 이유:
  - 현재 목표에서는 ProseMirror의 Decoration 기반 접근이 더 직접적임
  - 고스트 텍스트와 커스텀 편집기 동작 구현 시 참고할 수 있는 자료가 더 풍부하다고 판단함
- 얻는 점:
  - Ghost Complete 구현에 필요한 커스텀 편집기 제어에 유리
  - Headless 구조라 제품 UI를 자유롭게 구성 가능
  - 플러그인과 확장 중심 구조를 활용 가능
- 잃는 점:
  - ProseMirror 개념 이해가 필요함
  - 단순 입력창보다 구현 난도가 높음

### 2.3 스타일링 방식

- 선택 방향: Tailwind CSS
- 결정 상태: 확정
- 선택 이유:
  - MVP UI를 빠르게 구성하기 쉬움
  - 반응형 레이아웃 대응에 유리함
  - 단, 에디터 내부 스타일은 필요 시 별도 CSS를 병행함
- 선택하지 않은 후보:
  - 기본 CSS
- 선택하지 않은 이유:
  - MVP 초기 화면 구성 속도와 일관성 측면에서 Tailwind가 더 유리함
  - 반응형 레이아웃과 반복 UI 조합을 빠르게 정리하기 좋음
- 얻는 점:
  - 빠른 UI 구축
  - 일관된 간격, 크기, 반응형 규칙 적용
  - 컴포넌트 단위 스타일 작성 속도 향상
- 잃는 점:
  - 클래스가 길어질 수 있음
  - 에디터 내부처럼 세밀한 스타일 영역은 별도 CSS가 여전히 필요할 수 있음

### 2.4 상태 관리

- 선택 방향: React state
- 결정 상태: 확정
- 선택 이유:
  - 현재 MVP 범위에서 전역 상태 수가 많지 않음
  - 복잡한 상태는 전역 상태보다 편집기 로컬 인터랙션 상태에 가까움
  - 외부 상태 관리 도구 도입 없이도 충분히 시작 가능함
- 선택하지 않은 후보:
  - React Context 중심 구조
  - 외부 상태 관리 라이브러리
- 선택하지 않은 이유:
  - 모든 상태를 Context에 넣으면 리렌더 범위가 커질 수 있음
  - 외부 상태 관리 도구는 초기 복잡도 대비 효용이 낮음
  - 현재 MVP에서 진짜 어려운 문제는 전역 상태보다 편집기 상호작용임
- 얻는 점:
  - 구현 단순성 유지
  - 상태 경계를 로컬 기준으로 명확히 관리 가능
  - 불필요한 라이브러리 의존성 추가 방지
- 잃는 점:
  - 나중에 전역 상태가 늘어나면 구조 재정리가 필요할 수 있음
  - 여러 화면이 같은 상태를 복잡하게 공유하는 단계에서는 한계가 생길 수 있음

### 2.5 LLM 연동 방식

- 선택 방향: BYOK + 단일 원격 provider + fetch 기반 호출 + adapter 인터페이스
- 결정 상태: 확정
- 선택 이유:
  - MVP 범위에서 가장 단순한 LLM 연동 구조임
  - 특정 provider SDK 종속을 늦추면서도 구조를 먼저 잡기 쉬움
  - adapter 계층을 통해 추후 멀티 provider 확장이 가능함
- 선택하지 않은 후보:
  - OAuth 기반 연동
  - 로컬 LLM 동시 지원
- 선택하지 않은 이유:
  - OAuth는 인증, 세션, 권한 처리까지 포함되어 MVP 범위를 크게 키움
  - 로컬 LLM은 실행 환경, 성능 편차, 설치 지원까지 고려해야 해 초기 복잡도가 높음
  - 현재 MVP의 핵심은 모델 다양성보다 글쓰기 UX 검증에 있음
- 얻는 점:
  - 구현 범위 축소
  - 빠른 초기 검증 가능
  - 이후 provider 추가를 위한 기본 구조 확보
- 잃는 점:
  - 초기에는 provider 선택 폭이 제한됨
  - 로컬 실행 선호 사용자까지 바로 포용하긴 어려움

## 3. 확장 고려 항목

- OAuth 기반 연동
- 로컬 LLM 지원
- 멀티 provider 고도화

## 4. 결정 원칙

- MVP 구현에 필요한 최소 기술부터 선택한다.
- 확정되지 않은 기술은 합의 없이 설치하거나 초기화하지 않는다.
- 제품의 핵심 가치는 편집기 상호작용이므로 에디터 관련 선택을 우선한다.
- 모바일 앱 확장 가능성만으로 모노레포를 먼저 도입하지 않는다.

## 5. 향후 결정 대상

- 실제 provider 선택
- 로컬 LLM 지원 시점
- OAuth 도입 필요 여부
