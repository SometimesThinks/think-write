# ThinkWrite 기술-스택

## 1. 목적

이 문서는 ThinkWrite MVP 구현을 위한 기술 선택 현황을 정리한다.

기술 스택은 확정 항목과 미확정 항목을 구분해 관리한다.

## 2. 확정 항목

### 2.1 프레임워크

- 선택 방향: Next.js
- 결정 상태: 확정
- 선택 이유:
  - 프론트엔드와 서버 계층을 하나의 애플리케이션 안에서 함께 구성 가능
  - `.env` 기반 provider 연동과 API route 구현에 적합
  - 오픈소스 온보딩과 초기 개발 속도 측면에서 유리
- 선택하지 않은 후보:
  - 별도 백엔드 분리 구조
- 선택하지 않은 이유:
  - MVP 단계에서 구조 복잡도가 과도하게 증가함
  - 현재 범위에서는 단일 애플리케이션으로도 충분히 구현 가능함
- 얻는 점:
  - 프론트엔드와 서버 계층을 빠르게 함께 개발 가능
  - 초기 배포 및 온보딩 단순화
  - self-hosted 환경 변수 기반 설정에 유리
- 잃는 점:
  - 서버가 커질 경우 별도 서비스보다 구조적 한계가 빨리 드러날 수 있음

### 2.2 에디터

- 선택 방향: Tiptap
- 결정 상태: 확정
- 선택 이유:
  - Headless 구조로 심플한 글쓰기 UI 구성에 적합
  - ProseMirror 기반으로 고스트 텍스트 렌더링과 단축키 커스터마이징에 유리
  - 관련 문서와 사례가 비교적 풍부함
- 선택하지 않은 후보:
  - Lexical
- 선택하지 않은 이유:
  - 현재 목표에서는 ProseMirror의 Decoration 기반 접근이 더 직접적임
- 얻는 점:
  - Ghost Complete 구현에 필요한 커스텀 편집기 제어에 유리
  - Headless 구조라 제품 UI를 자유롭게 구성 가능
- 잃는 점:
  - ProseMirror 개념 이해가 필요함
  - 단순 입력창보다 구현 난도가 높음

### 2.3 스타일링 방식

- 선택 방향: Tailwind CSS
- 결정 상태: 확정
- 선택 이유:
  - MVP UI를 빠르게 구성하기 쉬움
  - 반응형 레이아웃 대응에 유리함
  - 단, 에디터 내부 스타일은 필요 시 별도 CSS를 병행함

### 2.4 상태 관리

- 선택 방향: React state
- 결정 상태: 확정
- 선택 이유:
  - 현재 MVP 범위에서 전역 상태 수가 많지 않음
  - 복잡한 상태는 전역 상태보다 편집기 로컬 인터랙션 상태에 가까움
  - 외부 상태 관리 도구 도입 없이도 충분히 시작 가능함

### 2.5 LLM 연동 방식

- 선택 방향: `.env` 기반 단일 원격 provider + fetch 기반 호출 + adapter 인터페이스
- 결정 상태: 확정
- 선택 이유:
  - MVP 범위에서 가장 단순한 LLM 연동 구조임
  - 앱 내부 BYOK UI 없이도 provider 연동을 빠르게 검증할 수 있음
  - adapter 계층을 통해 추후 멀티 provider 확장이 가능함
- 선택하지 않은 후보:
  - 앱 내부 BYOK 등록 UI
  - OAuth 기반 연동
  - 로컬 LLM 동시 지원
- 선택하지 않은 이유:
  - 앱 내부 BYOK는 key 저장/삭제/조회 UX와 보안 경계를 함께 구현해야 해 무거움
  - OAuth는 인증, 세션, 권한 처리까지 포함되어 MVP 범위를 크게 키움
  - 로컬 LLM은 실행 환경, 성능 편차, 설치 지원까지 고려해야 해 초기 복잡도가 높음
- 얻는 점:
  - 구현 범위 축소
  - 빠른 초기 검증 가능
  - 이후 provider 추가를 위한 기본 구조 확보
- 잃는 점:
  - 앱 내부 사용자별 BYOK UX는 아직 검증하지 못함
  - 초기에는 provider 선택 폭이 제한됨

### 2.6 초기 provider / model

- 선택 방향: OpenAI + `gpt-5-nano`
- 결정 상태: 확정
- 선택 이유:
  - 초기 MVP에서는 최고 품질보다 저비용 end-to-end 검증이 더 중요함
  - Ghost Complete와 editor 흐름을 빠르게 검증하기에 비용 부담이 낮음
  - OpenAI는 초기 통합 자료와 운영 레퍼런스가 풍부함
- 선택하지 않은 후보:
  - OpenAI 상위 모델
  - 타 provider 우선 도입
- 선택하지 않은 이유:
  - 상위 모델은 초기 실험 비용이 커짐
  - 타 provider 우선 도입은 초기 통합 안정성 측면에서 불확실성이 큼
- 얻는 점:
  - 매우 낮은 비용으로 반복 실험 가능
  - 최초 provider를 조기 고정해 API / adapter / UI 작업을 병렬로 진행하기 쉬움
- 잃는 점:
  - Ghost Complete 품질이 부족하면 상위 모델 재검토가 필요함

## 3. 확장 고려 항목

- 앱 내부 BYOK 등록 UX
- OAuth 기반 연동
- 로컬 LLM 지원
- 멀티 provider 고도화

## 4. 결정 원칙

- MVP 구현에 필요한 최소 기술부터 선택한다.
- 확정되지 않은 기술은 합의 없이 설치하거나 초기화하지 않는다.
- 제품의 핵심 가치는 편집기 상호작용이므로 에디터 관련 선택을 우선한다.

## 5. 향후 결정 대상

- 앱 내부 BYOK UX 도입 시점
- 로컬 LLM 지원 시점
- OAuth 도입 필요 여부
- `gpt-5-nano` 품질 부족 시 상위 모델 전환 시점
