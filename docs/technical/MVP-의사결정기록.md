# ThinkWrite MVP 의사결정 기록

- 작성일: 2026-03-21
- 목적: MVP 구현에서 반복적으로 흔들릴 수 있는 기준을 미리 고정한다.
- 상태: 확정

## 1. 최초 provider / model 선택

### 결정
- 최초 provider는 **OpenAI**로 한다.
- 최초 모델은 **`gpt-5-nano`**로 한다.

### 선택 이유
- MVP 초반에는 품질 최적화보다 **낮은 비용으로 빠르게 end-to-end 검증**하는 것이 더 중요하다.
- 현재 범위는 학습 언어 설정, Ghost Complete, provider 연동 검증이므로 초기에 과도한 모델 비용이 필요하지 않다.
- OpenAI는 초기 통합 자료와 레퍼런스가 풍부해 **첫 provider로 위험이 낮다**.

### 장점
- API 비용이 매우 낮아 반복 실험이 쉽다.
- 초기 provider를 빠르게 고정해 adapter / API / UI 작업을 진행하기 쉽다.
- Ghost Complete의 응답 흐름, debounce, stale response 처리 같은 제품 핵심 UX를 저비용으로 검증할 수 있다.

### 반대급부 / 단점
- `gpt-5-nano`는 매우 저렴한 대신 **문장 제안 품질이 부족할 가능성**이 있다.
- 향후 `gpt-5-mini` 또는 `gpt-4o-mini`로 상향이 필요할 수 있다.

### 추후 재검토 조건
- Ghost Complete 제안이 지나치게 부자연스럽거나 너무 짧을 때
- 사용자 테스트에서 “쓸 만한 다음 문장” 품질이 부족할 때

## 2. API Key 관리 정책

### 결정
- API Key는 앱 내부 BYOK 등록 UI로 받지 않는다.
- API Key는 **서버 `.env.local`**에서만 관리한다.
- 클라이언트에는 API Key 원문을 전달하지 않는다.

### 선택 이유
- 이 MVP는 다중 사용자 서비스 운영보다 **오픈소스 self-hosted 검증**이 우선이다.
- `.env.local` 방식이면 key 저장/조회/삭제 API, DB, 암호화 정책 없이도 빠르게 provider 연동을 검증할 수 있다.
- 현재 단계에서는 in-app BYOK UX보다 Ghost Complete 흐름 검증이 더 중요하다.

### 장점
- 구현 범위가 크게 줄어든다.
- key 저장용 DB, 암호화, 삭제 정책을 지금 당장 설계하지 않아도 된다.
- 브라우저나 클라이언트 응답에 key가 노출될 여지가 줄어든다.

### 반대급부 / 단점
- 앱 안에서 사용자가 직접 key를 등록/교체하는 BYOK UX는 검증하지 못한다.
- 진짜 다중 사용자 제품으로 확장할 때는 key 관리 방식을 다시 설계해야 한다.
- self-hosted 사용자는 `.env.local` 설정 방법을 알아야 한다.

### 대안과 비교
- **앱 내부 BYOK UI + 서버 저장**
  - 장점: 제품 안에서 사용자별 key 등록 경험까지 검증 가능하다.
  - 단점: MVP 단계에는 DB/암호화/조회 상태/삭제 UX까지 함께 구현해야 해 무겁다.
- **브라우저 저장(localStorage)**
  - 장점: 구현이 가장 단순하다.
  - 단점: key가 브라우저 환경에 남아 보안 경계가 약해진다.

### 추후 재검토 조건
- 실제 사용자별 key 등록 UX가 제품 범위에 들어올 때
- self-hosted 외 배포 운영 시나리오가 필요해질 때

## 3. Ghost Complete 오류 노출 정책

### 결정
- **정상 상태에서는 ghost text가 발동**하는 것이 기본이다.
- **provider 설정 누락 또는 API Key 인증 실패 같은 전역 문제에만 toast**를 사용한다.
- **ghost 요청 실패/무효화는 editor 근처 inline notice 또는 무표시**로 처리한다.

### 선택 이유
- ThinkWrite의 핵심은 “편집기 내부에서 흐름을 끊지 않는 경험”이다.
- toast는 전역 알림에는 유용하지만, 에디터 문맥과는 거리가 있다.
- 제안 실패나 무효화까지 전부 toast로 처리하면 글쓰기 흐름을 방해할 수 있다.

### 장점
- 정상 상태의 중심이 항상 editor/ghost text에 유지된다.
- 전역 설정 문제와 에디터 내부 흐름 문제를 구분해 보여줄 수 있다.
- 사용자는 “왜 제안이 안 나오는지”를 더 문맥적으로 이해할 수 있다.

### 반대급부 / 단점
- toast-only보다 UI 설계가 조금 더 복잡하다.
- inline notice를 어디에, 어느 톤으로, 얼마나 자주 보여줄지 추가 설계가 필요하다.

### 추후 재검토 조건
- inline notice가 과하게 눈에 띄어 집필 흐름을 해칠 때
- 전역 오류와 editor 내부 오류를 사용자가 잘 구분하지 못할 때

---

## 구현 시 바로 반영할 체크포인트

- OpenAI adapter는 최초 모델 `gpt-5-nano` 기준으로 설계하되, 상위 모델 교체가 쉬워야 한다.
- 서버는 `.env.local`의 `OPENAI_API_KEY`를 읽어 provider를 호출해야 한다.
- Ghost Complete 기본 UX는 “문제 없으면 ghost text 표시”여야 한다.
- toast는 provider 설정 누락 또는 인증 실패 등 전역 문제에 제한적으로 사용한다.
