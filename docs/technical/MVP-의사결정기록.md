# ThinkWrite MVP 의사결정 기록

- 작성일: 2026-03-21
- 목적: open questions에서 확정한 MVP 의사결정을 이후 구현/문서 정리에 바로 반영할 수 있도록 정리한다.
- 상태: 확정

## 1. 최초 provider / model 선택

### 결정
- 최초 provider는 **OpenAI**로 한다.
- 최초 모델은 **`gpt-5-nano`**로 한다.

### 선택 이유
- MVP 초반에는 품질 최적화보다 **낮은 비용으로 빠르게 end-to-end 검증**하는 것이 더 중요하다.
- 현재 범위는 학습 언어 설정, Ghost Complete, BYOK 연동 검증이므로 초기에 과도한 모델 비용이 필요하지 않다.
- OpenAI는 초기 통합 자료와 레퍼런스가 풍부해 **첫 provider로 위험이 낮다**.

### 장점
- API 비용이 매우 낮아 반복 실험이 쉽다.
- 초기 provider를 빠르게 고정해 adapter / API / UI 작업을 진행하기 쉽다.
- Ghost Complete의 응답 흐름, debounce, stale response 처리 같은 제품 핵심 UX를 저비용으로 검증할 수 있다.

### 반대급부 / 단점
- `gpt-5-nano`는 매우 저렴한 대신 **문장 제안 품질이 부족할 가능성**이 있다.
- Ghost Complete 특성상 “짧지만 자연스러운 다음 문장 제안”이 중요한데, 품질이 낮으면 UX 인상이 크게 나빠질 수 있다.
- 향후 `gpt-5-mini` 또는 `gpt-4o-mini`로 상향이 필요할 수 있다.

### 대안과 비교
- **OpenAI + 상위 모델**
  - 장점: 제안 품질 기대치가 더 높다.
  - 단점: 초반 실험 비용이 오른다.
- **다른 provider를 최초 선택**
  - 장점: 더 싼 요금제나 특정 모델 특성을 활용할 수 있다.
  - 단점: 초기 통합 안정성과 자료 측면에서 불확실성이 커진다.

### 추후 재검토 조건
- Ghost Complete 제안이 지나치게 부자연스럽거나 너무 짧을 때
- 사용자 테스트에서 “쓸 만한 다음 문장” 품질이 부족할 때
- 낮은 비용보다 문장 품질이 더 중요한 단계로 넘어갈 때

## 2. BYOK 저장 정책

### 결정
- API Key는 **브라우저에 저장하지 않는다**.
- API Key는 **서버 계층에서 영구 저장**한다.
- 단, **암호화 저장 / 원문 재노출 금지 / 삭제 가능**을 전제로 한다.

### 선택 이유
- 브라우저 저장은 구현은 단순하지만 API Key 노출 리스크가 더 크다.
- 사용자가 직접 키를 넣는 BYOK 구조라도, 제품은 가능한 한 **키 노출 위험을 줄이는 방향**으로 가는 것이 맞다.
- 이후 provider 호출 정책, 상태 관리, 오류 처리를 서버에서 일관되게 다루기 쉽다.

### 장점
- 브라우저 localStorage 등에 원문 키가 남지 않는다.
- 보안 경계가 명확해진다.
- provider 등록 상태 조회, 삭제, 향후 멀티 provider 확장에 유리하다.
- 클라이언트는 “등록 여부”만 알고, 실제 호출 책임은 서버가 진다.

### 반대급부 / 단점
- MVP 구현이 더 무거워진다.
- 저장소, 암호화, 삭제, 재노출 금지 정책을 함께 설계해야 한다.
- 단순한 로컬 저장 MVP보다 구현 시간이 더 든다.
- 오픈소스 프로젝트라 해도 실제 배포자는 서버/DB/비밀키 운영 책임을 져야 한다.

### 대안과 비교
- **브라우저 저장(localStorage 등)**
  - 장점: 구현이 단순하고 빠르다.
  - 단점: API Key가 사용자 브라우저 환경에 남아 노출 위험이 더 크다.
- **세션/요청 범위만 서버 보관**
  - 장점: 영구 저장보다 가볍고 보안 부담이 덜하다.
  - 단점: 재입력 UX가 나빠질 수 있고 BYOK 설정 기능의 완성도가 떨어진다.

### 추후 재검토 조건
- 초기 MVP에서 영구 저장 운영 부담이 과도할 때
- 사용자별 저장 정책/암호화 키 운영 방식이 과하게 복잡해질 때
- self-hosted 시나리오에서 더 단순한 대안이 필요할 때

## 3. Ghost Complete 오류 노출 정책

### 결정
- **정상 상태에서는 ghost text가 발동**하는 것이 기본이다.
- **API Key 인증 실패 같은 전역/설정성 문제에만 toast**를 사용한다.
- **ghost 요청 실패/무효화는 editor 근처 inline notice 또는 무표시**로 처리한다.

### 선택 이유
- ThinkWrite의 핵심은 “편집기 내부에서 흐름을 끊지 않는 경험”이다.
- toast는 전역 알림에는 유용하지만, 에디터 문맥과는 거리가 있다.
- 제안 실패나 무효화까지 전부 toast로 처리하면 글쓰기 흐름을 방해할 수 있다.

### 장점
- 정상 상태의 중심이 항상 editor/ghost text에 유지된다.
- 전역 설정 문제와 에디터 내부 흐름 문제를 구분해 보여줄 수 있다.
- 사용자는 “왜 제안이 안 나오는지”를 더 문맥적으로 이해할 수 있다.

### 반대급부 / 단점
- toast-only보다 UI 설계가 조금 더 복잡하다.
- inline notice를 어디에, 어느 톤으로, 얼마나 자주 보여줄지 추가 설계가 필요하다.
- 너무 많은 inline 상태를 만들면 오히려 에디터가 산만해질 수 있다.

### 대안과 비교
- **toast 우선 정책**
  - 장점: 구현이 단순하고 전역 처리에 쉽다.
  - 단점: 에디터 맥락과 분리되어 제품 방향과 덜 맞다.
- **모든 오류를 inline으로만 처리**
  - 장점: 편집 맥락 일관성은 높다.
  - 단점: API Key 인증 실패 같은 전역 문제까지 에디터 내부 문제처럼 보일 수 있다.

### 추후 재검토 조건
- inline notice가 과하게 눈에 띄어 집필 흐름을 해칠 때
- 전역 오류와 editor 내부 오류를 사용자가 잘 구분하지 못할 때
- 실제 사용자 테스트에서 toast가 더 이해하기 쉽다는 근거가 나올 때

## 구현 시 바로 반영할 체크포인트

- OpenAI adapter는 최초 모델 `gpt-5-nano` 기준으로 설계하되, 상위 모델 교체가 쉬워야 한다.
- API Key는 서버 영구 저장, 암호화, 삭제 가능, 원문 재노출 금지 정책을 만족해야 한다.
- Ghost Complete 기본 UX는 “문제 없으면 ghost text 표시”여야 한다.
- toast는 API Key 인증 실패 등 전역 문제에 제한적으로 사용한다.
