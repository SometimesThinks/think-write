# ThinkWrite 백엔드-의사결정기록

## ADR-001: Next.js BFF 채택

### 결정

별도 Nest.js 서비스 대신 Next.js 기반 BFF 구조로 시작한다.

### 이유

- 프론트엔드와 서버 계층을 한 저장소에서 빠르게 개발 가능
- 오픈소스 온보딩이 단순함
- 1인 개발 초기 단계에서 운영 복잡도를 낮춤

### 추후 재검토 조건

- 장기 실행 서버 작업 필요
- 인증, 권한, 멀티유저 기능 확장
- 서버 복잡도가 독립 서비스 수준으로 증가

## ADR-002: Provider Adapter 계층 도입

### 결정

LLM provider별 차이를 adapter 계층에서 흡수한다.

### 이유

- OpenAI 외 provider 지원 여지 확보
- 프론트엔드와 상위 유스케이스의 provider 종속성 제거
- provider 교체 시 route 상위 계층 변경 최소화

## ADR-003: provider key 관리 방식

### 결정

초기 MVP에서는 앱 내부 key 저장 API를 두지 않는다.
provider key는 서버 `.env.local`에서만 읽는다.

### 이유

- 현재 목표는 다중 사용자 BYOK UX보다 Ghost Complete 흐름 검증이다.
- DB, 암호화, 삭제, 조회 상태 API 없이도 provider 연동을 빠르게 구현할 수 있다.
- 클라이언트가 key 원문을 다루지 않게 해 보안 경계를 단순화할 수 있다.

### 추후 재검토 조건

- 앱 내부 BYOK 등록 UX가 제품 범위에 들어올 때
- 사용자별 key 분리 저장이 필요해질 때
- 배포 운영 형태가 self-hosted를 넘어설 때

## ADR-004: 초기 provider / model 고정

### 결정

초기 MVP provider는 OpenAI로 고정하고, 최초 completion 모델은 `gpt-5-nano`를 사용한다.

### 이유

- MVP 초기 단계에서는 최고 품질보다 저비용 end-to-end 검증이 더 중요함
- editor UX, Ghost Complete 흐름, `.env` 기반 provider 연동을 빠르게 검증하기 쉬움
- OpenAI는 초기 통합 자료와 운영 레퍼런스가 풍부함

### 추후 재검토 조건

- Ghost Complete 품질이 부족할 때
- 더 높은 문장 품질이 제품 핵심 KPI가 되는 단계로 넘어갈 때
